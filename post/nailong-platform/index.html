NaiLong-platform 概述 🚀

0. NaiLong-platform 是什么？ 🤔

NaiLong-platform 是一个 自研的，用 Spring Boot 3 实现的 招新平台后端：

  • 🌐 覆盖范围广：
    • 覆盖 后端常用功能，如 邮箱验证码注册 / 登录、JWT 双 Token、题目答题、排行榜、公告
    • 覆盖招新场景里的 常见题型，如 选择题、Flag 题、附件题
  • 🔧 工程上的选择：
    • 使用 Spring Security 做 认证授权，过滤器链 里挂上 JWT 过滤器和 IP 黑名单
    • 使用 MyBatis-Plus 做 持久化，表结构在 sql/schema.sql
    • 分层是 Controller → Service → Mapper，接口注释用 Doxygen 风格（@brief / @param / @return，字段用 ///<）
  • 📬 缓存和并发：
    • 使用 Redis（StringRedisTemplate）存 Token、验证码、题目缓存、排行榜 ZSet
    • 使用 Redisson 分布式锁 防 重复提交
    • 使用 Caffeine 做 本地缓存（配置里可以开启）
    • 另有 RedisUtils 用内存 Map 模拟 Redis API，给部分用户 缓存 场景 兜底
  • 📝 注释友善：
    • 类 / 方法用 @brief 等 Doxygen 标签
    • 字段、注解属性用行尾 ///<
    • 关键流程在实现里用 // 写 -> 步骤
  • 📖 接口文档：
    • 开发环境集成 Knife4j，浏览器打开 /api/doc.html 可 调试（dev / prod 常带 context-path: /api）
    • 文字说明在仓库 docs/API.md、docs/架构设计.md
  • ✅ 测试：
    • 具有部分 Service 单测（认证、题目、排行榜、密码工具等）

源码：MilLoong/NaiLong-platform

1. 为什么要学 NaiLong-platform？ 🎯

NaiLong-platform 主要是用于：

  • 🏗️ 学习 Spring Boot 招新 / CTF 平台 一类业务怎么拆开模块
  • 💻 学习 JWT 双 Token、Redis 排行榜、分数 衰减、限流 和防 重复提交 在真实项目里怎么落地
  • 📄 求职中的 项目简历

2. NaiLong-platform 适合人群？ 👥

NaiLong-platform 主要适合：

  • 🌱 对 Java / Spring 有所了解，但 不知道招新平台后端从哪下手 的
  • ✨ 想熟悉认证、缓存、排行榜，但 不想只做纯 CRUD 管理后台 的
  • 🧩 想知道招新答题平台 的 基本方案 的

NaiLong-platform 不适合：

  • 🚫 已经在搭 大型微服务招新 / OJ 集群 的高级工程师当 唯一教材

3. 项目前置知识 📚

本项目 需要的知识包括：

  • 💻 Java： 类、集合、异常、注解（必备），了解 Spring Bean / 依赖注入
  • 📦 会碰到的库（可选）：
    • Spring Boot 3 / Spring MVC：HTTP 接口
    • Spring Security：过滤器链、角色权限
    • MyBatis-Plus：LambdaQueryWrapper、分页、逻辑删除
    • jjwt：签发 / 解析JWT
    • Redis / Redisson：缓存、ZSet、分布式锁
    • Knife4j：OpenAPI 文档
    • Hutool：部分工具（如 BeanUtil、RandomUtil）
  • 🔨 构建：
    • 会用 Maven 编译和运行（必备）
    • JDK 17+
  • 🌐 后端常识： 知道 HTTP（GET / POST、JSON、状态码）和 MySQL 增删改查（必备）
  • 📬 中间件概念： 知道 Redis 是缓存、ZSet 能做 排行榜（建议先有印象）
  • 🐳 环境： Docker Compose 或本机 MySQL 8、Redis（必备）。仓库有 docker/docker-compose.yml

  • 再看 Mapper（接口 + resources/mapper XML）
  • 📋 再看 接口规范（路径、方法、JSON；也可以看 docs/API.md）

1.1 统一响应 Result 📦

HTTP 接口统一返回 Result<T>，字段包括 code、message、data、timestamp

相关函数：

  • Result.success()：构造 code=200 且无 data 的 成功 包

    • 构造时自动 写入 当前毫秒时间戳

    • 骨架：

      // TODO: new Result<>(200, "操作成功")
// TODO: timestamp = System.currentTimeMillis()

  • Result.success(T data) / Result.success(String message, T data)：成功 并携带业务数据

    • message 可覆盖默认文案，便于登录 / 注册等场景 返回 友好提示

    • 骨架：

      // TODO: code 固定 200
// TODO: 把 VO / 分页对象放进 data

  • Result.fail(...) / Result.build(code, message, data)：失败 或自定义状态

    • 业务层常配合 BusinessException 的 code，全局处理器再 Result.build

    • 骨架：

      // TODO: 业务失败时 throw new BusinessException(ResultCode.xxx)
// TODO: GlobalExceptionHandler 捕获后映射成 Result

  • isSuccess()：判断是否 成功（code == 200）

1.2 业务状态码 ResultCode 🔢

枚举在 com.nailong.common.enums.ResultCode，与 HTTP 状态码、业务码 混用

注：

  • Service 抛 BusinessException 时使用这里的 code
  • 前端可按区间识别：1xxx 用户、2xxx 题目、3xxx 排行、4xxx 公告、9xxx 系统
  • SUCCESS(200)（SUCCESS）
    • 数值 / 文案： 200 / 操作成功
    • 典型场景： 所有正常返回
  • BAD_REQUEST(400)（BAD_REQUEST）
    • 数值 / 文案： 400 / 请求参数错误
    • 典型场景： @Validated 失败 或手动 校验
  • UNAUTHORIZED(401)（UNAUTHORIZED）
    • 数值 / 文案： 401 /未授权
    • 典型场景： 未带 Token 或 会话 失效
  • FORBIDDEN(403)（FORBIDDEN）
    • 数值 / 文案： 403 / 权限不足
    • 典型场景： @PreAuthorize 拒绝
  • USER_NOT_FOUND(1001)（USER_NOT_FOUND）
    • 数值 / 文案： 1001 / 用户不存在
    • 典型场景： 查库为空或账号 禁用
  • USER_ALREADY_EXISTS(1002)（USER_ALREADY_EXISTS）
    • 数值 / 文案： 1002 / 用户已存在
    • 典型场景： 注册用户名冲突
  • INVALID_PASSWORD(1003)（INVALID_PASSWORD）
    • 数值 / 文案： 1003 / 密码错误
    • 典型场景： Security 凭证异常 映射
  • EMAIL_ALREADY_EXISTS(1005)（EMAIL_ALREADY_EXISTS）
    • 数值 / 文案： 1005 / 邮箱已被注册
    • 典型场景： 注册邮箱冲突
  • INVALID_VERIFICATION_CODE(1006)（INVALID_VERIFICATION_CODE）
    • 数值 / 文案： 1006 /验证码 错误或已 过期
    • 典型场景： Redis 中无码或不匹配
  • TOKEN_INVALID(1008)（TOKEN_INVALID）
    • 数值 / 文案： 1008 / 无效的Token
    • 典型场景： 刷新时 Redis 与 JWT 不一致
  • ACCOUNT_DISABLED(1009)（ACCOUNT_DISABLED）
    • 数值 / 文案： 1009 / 账号已被 禁用
    • 典型场景： 登录或刷新时 status=0
  • ACCOUNT_LOCKED(1010)（ACCOUNT_LOCKED）
    • 数值 / 文案： 1010 / 账号已被 锁定
    • 典型场景： 登录 失败 次数达到上限
  • PROBLEM_NOT_FOUND(2001)（PROBLEM_NOT_FOUND）
    • 数值 / 文案： 2001 / 题目不存在
    • 典型场景： 题目隐藏或 id 无效
  • PROBLEM_ALREADY_SOLVED(2002)（PROBLEM_ALREADY_SOLVED）
    • 数值 / 文案： 2002 / 已完成该题
    • 典型场景： 已有 ACCEPTED 提交
  • RATE_LIMIT_EXCEEDED(9001)（RATE_LIMIT_EXCEEDED）
    • 数值 / 文案： 9001 / 访问频率 超限
    • 典型场景： RateLimitAspect 触发
  • IP_BLOCKED(9002)（IP_BLOCKED）
    • 数值 / 文案： 9002 / IP 已被封禁
    • 典型场景： IpBlacklistFilter 拦截
  • REPEAT_SUBMIT(9003)（REPEAT_SUBMIT）
    • 数值 / 文案： 9003 / 请勿 重复提交
    • 典型场景： RepeatSubmitAspect 拦截

1.3 全局异常 GlobalExceptionHandler 🛡️

@RestControllerAdvice 把异常 统一 转成 Result，并设置 HTTP 状态

  • handleBusinessException：捕获 BusinessException

    • 记录 warn 日志，带上请求 URI

    • 返回 Result.build(e.getCode(), e.getMessage(), null)，HTTP 400

    • 骨架：

  • handleValidationException / handleBindException：参数 校验失败

    • 映射 ResultCode.BAD_REQUEST

  • handleAuthenticationException / handleAccessDeniedException：401 / 403

  • handleRuntimeException / handleException：兜底 500，避免栈信息泄露给客户端

1.4 JwtUtil 🔑

基于 jjwt 签发 / 解析 Access 与 Refresh 双 Token

  • generateAccessToken(userId, username, role)：claims 含 type=access，签发 Access Token
  • generateRefreshToken(userId)：claims 仅 userId 与 type=refresh，签发 Refresh Token
  • validateToken / isAccessToken / isRefreshToken：过滤器与刷新接口做 校验 / 类型判断
  • parseToken：签名 校验失败、过期、格式错误时抛运行时异常并打日志

配置项来自 nailong.jwt.secret、access-token-expire、refresh-token-expire、issuer

  • 骨架：

// TODO: createToken 设置 iss / iat / exp，HS256 签名
// TODO: validateToken 先 parse 再判断 exp 是否过期

16.1 路径前缀差异说明 🧭

Controller 类前缀并不统一：

  • 认证/ 题目 / 排行 / 公告：短前缀（/auth、/problems、/rank、/notices）
  • 用户 / 提交：带 /api（/api/users、/api/submission）
  • 设备 / 日志：带版本段（/api/v1/device、/api/v1/log）

联调时建议：

  • 先看当前 profile 有没有 context-path: /api
  • 再在 Knife4j 里点一次真实请求，对照浏览器地址栏
  • 前端 axios baseURL 不要和类前缀重复叠 /api

注： Security 白名单 写的是 去掉 context-path 之后 的 servlet 路径（如 /auth/login），配了 context-path 后过滤器匹配仍按去掉前缀的路径算
