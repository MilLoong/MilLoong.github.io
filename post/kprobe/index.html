深入理解 Linux Kprobe

介绍

简要介绍

Kprobe 让你在 几乎任意 内核指令地址 上 动态打断点，命中时执行你提供的 pre_handler / post_handler，在 尽量少破坏现场 的前提下 采集信息

常见写法是做成一个 内核模块：init 里 register_*probe，exit 里 unregister_*probe

内核需要打开 CONFIG_KPROBES，并且支持 模块加载卸载

探针形态

现在文档里主推两类：

形态 作用
kprobe 挂在 任意内核指令（常挂 函数入口，也可挂 函数中间某条）
kretprobe（返回探针） 在目标函数 返回 时打回调

历史上还有 jprobe（函数入口、参数签名对齐 的一种 封装），现已 弃用

特点和注意事项

  • 动态： 运行时 插入 / 删除，适合临时看一条 内核路径
  • 覆盖面广： 很多 内核函数 都能挂，但仍有 黑名单
  • 符号不稳定： 函数名、参数、角色 会随 内核版本 变，脚本 跨版本 可能挂不上
  • 改执行流危险： 在 pre_handler 里改 regs 的 指令指针（x86_64 上是 RIP）可以跳走，但 栈帧、并发、架构细节 都要自己去想办法兜底

有稳定 tracepoint 时，优先用 tracepoint

Kprobe 更适合 没有 现成追点（tracepoint）、又必须盯某条 内核路径 的时候

原理

注册时发生了什么

以常见架构为例（x86 用 int3）：

  1. 把 探测点 上的 原指令拷一份 存起来
  2. 把 原指令开头 若干字节 换成 断点指令（x86：int3，操作码 0xcc）
  3. 之后 CPU 跑到这里就会进 陷阱（trap），再交给 Kprobe 框架
  flowchart TB
    A["register_kprobe"] --> B["解析 symbol_name 或 addr"]
    B --> C["拷贝原指令到指令槽"]
    C --> D["用断点指令盖住探测点首字节"]
    D --> E["等待命中"]

命中后的执行顺序

一次典型 kprobe 命中：

  1. CPU 撞上断点，保存 寄存器，进入 Kprobe
  2. 调用 pre_handler（此时 原指令 还没真正按原样执行完）
  3. 在 指令副本 上 单步执行 被探测 的 那条指令（不在原址临时 撕掉断点 再 单步，是为了 避免 多核窗口 里别的 CPU 从 断点空档 穿过去）
  4. 若有 post_handler，单步结束 后再去调用
  5. 从探测点 下一条指令 继续往下跑
  flowchart TB
    A["CPU 执行到断点"] --> B["pre_handler"]
    B --> C{"pre_handler 返回值"}
    C -->|0| D["单步执行指令副本"]
    C -->|非 0| E["认为已改执行路径，跳过单步"]
    D --> F["post_handler（若有）"]
    F --> G["回到探测点之后继续执行"]
    E --> G

若在 pre_handler 里改了 指令指针，并返回 非 0，框架会 跳过单步 和 post_handler，直接按你 设好的地址 回去

kretprobe：怎么钩返回

register_kretprobe() 本质上会在函数 入口 先挂一个 kprobe：

  1. 入口命中时，把真正的 返回地址 存进 kretprobe_instance
  2. 把 栈上（或对应位置）的返回地址 改成 trampoline
  3. 函数 ret 时先落到 trampoline，再跑你的 返回 handler
  4. 最后把 指令指针 恢复成 当初保存 的 返回地址

注册前要设好 maxactive：同时允许多少个 已进入、尚未返回 的实例，太小会丢事件，丢的次数记在 nmissed

还可以设可选的 entry_handler：入口回调 返回 0 才保证这次调用会配一个 返回回调，返回非 0 则这次 不再跟 返回探针

跳转优化与黑名单

在打开 CONFIG_OPTPROBES、且 debug.kprobes_optimization=1 时，框架可能把 断点 优化成跳转，跳到一段 detour 缓冲里跑 handler，降低 热点开销

优化 有 安全检查（优化区 不能有 乱入跳转、异常回流 等），有 post_handler 等条件时也可能 不优化

黑名单： Kprobe 不能 无脑挂在实现 Kprobe 自己的代码上，否则容易 递归陷阱，内核用 NOKPROBE_SYMBOL() 等机制维护 黑名单，注册时撞上会 失败

源码要点

路径以 upstream Linux 为准，具体 行号 随 版本 会略微不同，对照 符号名 即可

struct kprobe 关键字段

头文件：include/linux/kprobes.h

struct kprobe {
    kprobe_opcode_t *addr;           // 探测点地址
    const char *symbol_name;         // 按符号名解析（与 addr 二选一）
    unsigned int offset;             // 相对符号的字节偏移
    kprobe_pre_handler_t pre_handler;
    kprobe_post_handler_t post_handler;
    kprobe_opcode_t opcode;          // 被替换掉的原操作码
    struct arch_specific_insn ainsn; // 架构相关：指令副本槽等
    u32 flags;
    unsigned long nmissed;
    /* ... */
};

约定：

  • symbol_name 和 addr 只能给一个，两个都给会 -EINVAL
  • 可用 offset 挂到 符号内部 某条指令（CISC 上要自己保证 对齐 指令边界）

注册：register_kprobe

对外入口是 register_kprobe(p)，大致会做这些事：

  1. 用 symbol_name / offset 或 addr 算出 最终探测地址
  2. 做 地址安全检查（是否 可探测、是否落在 模块文本 等）
  3. 架构侧 prepare：拷贝 原指令、准备 指令槽
  4. 链入内部表，再 arm：真正 把 断点 写进 探测点

流程可以看成：

解析地址 -> 安全检查 -> prepare -> 挂表 -> arm 断点

实现见 kernel/kprobes.c 里的 register_kprobe

卸载对称：unregister_kprobe → 先 disarm，再删除 架构侧指令槽

x86：写成 int3，再进 handler

x86 上和 插桩 直接相关的几步：

  • arch_prepare_kprobe：检查地址，从 get_insn_slot() 拿 可执行槽，拷贝指令
  • arch_arm_kprobe：用 text_poke 把 探测点 第一字节 写成 0xcc（int3），并做 多核同步
  • arch_disarm_kprobe：把原 opcode 写回去

arm 时的 核心动作 可以理解成：

void arch_arm_kprobe(struct kprobe *p) {
    kprobe_opcode_t int3 = BREAKPOINT_INSTRUCTION; // 0xcc
    text_poke(p->addr, &int3, 1);
    // 再保证各 CPU 看见新指令
}

命中断点 后进 kprobe_int3_handler：

  1. 用户态 则交给 别的路径
  2. 用 ip - 1 找到 探测点 对应的 struct kprobe
  3. 调 pre_handler
  4. 返回 0 则准备 单步执行 指令副本，非 0 则认为 已经改过 执行路径
  5. 返回 1 表示这个 异常 已被 kprobe 吃掉

实现见 arch/x86/kernel/kprobes/core.c

单步跑完 副本 后，会走到 post 处理，再把 执行流 接回 探测点后面 的 指令

kretprobe 注册

register_kretprobe(rp) 会：

  1. 校验 maxactive / handler
  2. 预分配一批 kretprobe_instance（maxactive <= 0 时落到和 NR_CPUS 相关的默认值）
  3. 给 rp->kp 配好入口逻辑后，再 register_kprobe(&rp->kp)

入口命中时 换返回地址，trampoline 上的 探针 再触发 返回 handler

应用

内核模块示例

内核树自带示例：samples/kprobes/kprobe_example.c

思路：对 kernel_clone（可用 模块参数 改 符号名）挂 pre_handler / post_handler，命中时 pr_info 打出 地址 和 部分寄存器

模块骨架 大概是：

static struct kprobe kp = {
    .symbol_name = "kernel_clone",
};

static int __init kprobe_init(void) {
    kp.pre_handler = handler_pre;
    kp.post_handler = handler_post;
    return register_kprobe(&kp);
}

static void __exit kprobe_exit(void) {
    unregister_kprobe(&kp);
}

加载后看 dmesg：每次 创建进程 走到 kernel_clone 就会打一行

示例模块需 GPL，且 内核 要编进 sample，或 自己拷贝 出来用对应 headers 编译

perf probe

不必手写模块 时，可以用 perf probe 在 内核函数 上 定义 动态事件，再 perf record / perf trace：

# 查看某函数里哪些行可探（有 debuginfo 更友好）
perf probe --line schedule

# 在 schedule 某行挂探，并采一个字段（示例）
perf probe --add='schedule:12 cpu'

perf probe --list
perf probe --del='schedule*'

底层仍会走到 kprobe / ftrace 的 kprobe 事件机制，权限上通常要能用 tracefs 和 kallsyms

bpftrace

bpftrace 把 kprobe / kretprobe 收成 脚本语法，适合 快速摸路径：

# 函数入口
bpftrace -e 'kprobe:vfs_read { @[comm] = count(); }'

# 函数返回，看返回值分布
bpftrace -e 'kretprobe:vfs_read { @bytes = hist(retval); }'

和裸 Kprobe 一样：符号随内核变，能稳定用 tracepoint 的地方，优先 tracepoint:，避免因为 版本 而出错

和 eBPF、SystemTap 的关系

  • eBPF： 很多 kprobe / kretprobe 程序类型，最终仍依赖 内核探测框架，再叠加 验证器、映射表 等
  • SystemTap： 高层脚本，后端 可降到 kprobe 等
  • 自己改流程： 仅在 pre_handler 里改 regs 并返回非 0，生产环境 更常见的是 只读观测，少改控制流
