NLOJ 概述 🚀

0. NLOJ 是什么？ 🤔

NLOJ 是一个 自研的，用 C++20 实现的 轻量级 OJ（Online Judge）后端：

  • 🌐 覆盖范围广：
    • 覆盖 后端常用功能，如 用户鉴权、题目管理 CRUD、沙箱判题 等
    • 覆盖 OJ 中的常见题型，如 标准题、交互题、通信题、Special Judge
  • 🔧 工程上的选择：
    • 使用 RAII 管理 连接 等资源，减少 泄漏 和 手工释放
    • 使用 CMake 多模块 拆开 用户 / 题目 / 提交 / 判题，方便对照着看
  • 📬 缓存和消息队列：
    • 使用 Redis 缓存题目，用来扛 读多写少
    • 使用 RabbitMQ 把 提交 和 判题 拆开：接口先 返回，评测放 后台 做
  • 📝 注释友善：
    • 头文件用 Doxygen（@brief / @param / @return）注释接口怎么用
    • 实现里用 // 写步骤，方便对照着去读
  • 📖 接口文档：
    • 给人看的 HTTP 说明：docs/api.md（路径、JSON、错误码）
    • 自带 Swagger UI，浏览器打开 /api/docs 就能调试登录、交题
    • 机器契约是 docs/openapi.yaml
  • ✅ 测试：
    • 具有 单元测试、集成测试、端到端测试 等常用软件测试
    • 具有 压力测试，用来看读题性能

1. 为什么要学 NLOJ？ 🎯

NLOJ 主要是用于：

  • 🏗️ 学习 后端项目架构
  • 💻 学习 C++ 在真实项目里怎么用
  • 📄 求职中的 项目简历

2. NLOJ 适合人群？ 👥

NLOJ 主要适合：

  • 🌱 对 C++ 语法有所了解，但 不知道从何开始架构和写项目 的 初学者
  • ✨ 想熟悉后端常见能力，但 不想只做管理后台 CRUD 的
  • 🧩 想知道市面上 OJ 产品，比如 力扣、POJ 等的 基本方案 的

NLOJ 不适合：

  • 🚫 搭建 系统化工程业务项目 的 高级工程师

3. 项目前置知识 📚

本项目 需要的知识包括：

  • 💻 C++： 类、STL、指针 / 引用、基本语法（必备），了解 RAII、智能指针
  • 📦 会碰到的库（可选）：
    • nlohmann/json：配置和 HTTP 里的 JSON
    • cpp-httplib：HTTP 服务
    • OpenSSL：密码 PBKDF2、JWT 的 HMAC
    • MySQL C API（libmysqlclient）：连 MySQL 数据库
    • rabbitmq-c：连 消息队列
    • 标准库：
      • std::mutex / std::lock_guard：配置、连接池等
      • std::atomic：缓存命中统计、判题节点状态
      • std::thread：判题节点里起后台线程
  • 🔨 构建：
    • 会用 CMake 配置、编译（必备）
    • 自己写 CMakeLists.txt（可选）
    • 编译器：Windows 用 VS2022（仓库有 CMakePresets.json），Linux 用 g++（由 CMake 去调用）
  • 🌐 后端常识： 知道 HTTP（GET / POST、JSON、状态码）和 MySQL 的 增删改查（必备）。索引、事务、JWT 原理（可选）
  • 📬 中间件概念： 知道 Redis 是缓存、消息队列用来 异步解耦（建议先有印象）。具体命令、交换机怎么配（可选）
  • 🐳 环境： Docker Desktop（或本机装好 MySQL 8、Redis、RabbitMQ）能跑起来（必备）。仓库根目录有 docker-compose.yml，docker compose up -d 一次拉起即可；镜像、网络怎么配（可选）

1.1 配置 ⚙️

配置 是给整个进程用的 运行参数：

  • HTTP 听哪个端口、签发 JWT 用哪把密钥、MySQL / Redis / RabbitMQ 连哪、用哪个账号

1.2 错误码 ❌

业务函数失败 时，用 枚举类型 AppError 表示 “出了什么事”

具体来说：像 注册、登录 失败时，返回值通常是 -1、空 token，不会 把 “用户名已存在” 当成函数返回值。所以公共模块提供了 枚举 + 相关函数，让 业务 只记 原因，HTTP 层 再填进 统一响应。

相关函数：

  • set_error(err, value)：把 value 写进调用方传入的指针；err 是 nullptr 就什么都不做（测试可以不传）

    • 这里的 err 是 指针出参，用来改调用方外面的那个 AppError，比如：

      AppError err = AppError::Ok;
set_error(&err, AppError::UsernameTaken);
// 此时 err == AppError::UsernameTaken

set_error(nullptr, AppError::Database);
// 什么都不做，方便测试不传 err

  • http_code(err)：把 AppError 映射成 JSON 里的数字 code（0 / 40000 / 40100 …）

  • http_message(err)：把 AppError 映射成给客户端看的短中文 message

  • 骨架：

1.3 MySQL 🐬

MySQL 处理 连接 和 发语句：

  • 连接从 池子 里借，用完还回去
  • 往库发 SELECT / INSERT 等

public:
    MysqlConn();
    ~MysqlConn();
    MysqlConn(const MysqlConn&) = delete;
    MysqlConn& operator=(const MysqlConn&) = delete;

        flowchart TB
    A[校验长度和字符集] -->|不过 set_error InvalidArgument| F[返回 -1]
    A -->|过了| B[MysqlConn]

    E -->|失败 set_error Database| F
    E -->|成功 set_error Ok| G[返回 insert_id]

      • username：长度 3～32，且上面的 username_charset_ok 为 1
      • password：长度 6～64
      • 出现错误：set_error(err, InvalidArgument)，return -1

    • 2. 借连接

      • 定义 nloj::common::MysqlConn conn
      • 构造 时从连接池 acquire 一条，析构 时自动 release 还回去
      • conn.ok() 为 0：没借到（池空、连不上库等），set_error(err, Database)，return -1
      • 后面 查重 / INSERT 用 conn.get() 拿到 MYSQL*，再交给 query_stmt

    • 3. 查重 username

      • SQL：SELECT id FROM user WHERE username=? AND deleted=0 LIMIT 1
      • 条件含义：
        • username=?：按请求里的用户名查
        • deleted=0：只认 未软删 的行，已删用户名可以再注册
        • LIMIT 1：只取一条，用来判断有没有
      • args 放 {username}，走 query_stmt
      • query_stmt 失败：set_error(err, Database)，return -1
      • rows 非空：set_error(err, UsernameTaken)，return -1

    • 4. 密码哈希

      • 明文 不会 进库，只存 crypto::hash_password 结果到 password_hash

      • 返回空串：set_error(err, Internal)，return -1

      • SQL：INSERT INTO user (username, password_hash) VALUES (?, ?)

5.4.1 SPJ（STANDARD + SPJ）

用户程序仍按 标准题 跑完

对不对 不靠字符串精确比，靠出题人的 checker

  • 容器内 / 本机跑用户程序：runner 模式 std（和精确题一样）
  • 用户程序跑通（verdict == "OK"）后，宿主 run_host_spj：
    • 信任侧编译 checker.cpp（出题人代码，不进用户沙箱限额叙事）
    • 对每个仍为 OK 的用例执行：checker in_k.txt out_k.txt ans_k.txt
    • 退出码非 0 → 该用例改成 WA；checker 超时 / 编译失败 → 整次 SYSTEM_ERROR
  • run_judge_task 对 SPJ 不再 调 judge_outputs_match

5.4.2 交互（INTERACTIVE）

每用例同时跑 用户程序 和 交互器，用两根 pipe 对调 stdin / stdout

  • 交互器命令行带上本用例 in_k.txt（题目输入给交互器，不直接喂用户）
  • 两边都用 wait4 / waitpid 轮询；超时则两边都杀，记 TLE
  • 用户被 SIGKILL → MLE；用户非 0 退出 → RE
  • 交互器非 0 退出 → WA（交互器裁定错）；两边都 0 → OK
  • 结论已在容器内给出，run_judge_task 不再 做输出串比对

    D -->|"用户非 0"| R["RE"]
    D -->|"交互器非 0"| W["WA"]
    D -->|"都 0"| O["OK"]

5.4.3 通信（COMMUNICATION）

每用例跑 alice、bob、manager 三个进程，用四条 fifo 接线

  • code 必须能用上面的 split_comm_sources 拆开；extra_code 是管理器
  • 管理器参数：in_k.txt + 四条 fifo 路径
  • 超时杀三个进程 → TLE
  • alice / bob 任一侧 SIGKILL → MLE；任一侧非 0 → RE
  • 管理器非 0 → WA；全 0 → OK
  • 内存取 alice / bob ru_maxrss 较大者
