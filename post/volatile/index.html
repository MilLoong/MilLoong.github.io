C 语言：深入理解 volatile 关键字

前言

写过 C 的各位相信对 volatile 不陌生，它的 本质 是：

  • 对 volatile 修饰的对象，每一次 读、写 都必须 真正访问 内存中的对象
  • 禁止 编译器 把 值 长期 缓存到 寄存器，也 禁止 把对它的访存 合并、删掉

所以它做的是 抑制 编译器优化，并不是 让修改对别的线程自动可见

有人一遇到 线程同步 就加 volatile，这种看法是错的，volatile 不是 锁，不是 原子变量，也 不提供 内存屏障意义上的 跨线程同步

实际上，后面会讲到，除了特定场景外，我们不应该多去使用 volatile

基础

定义

volatile 本身英文意思是 易变的。从语义上说，它适用于 值 可能在 当前代码路径之外 发生变化 的对象，防止编译器按 这个变量不会自己变 去做错误优化

它的约束可以概括成：

  • 读：每次用到值，都要从 对象所在内存 重新读，不能沿用 旧寄存器 里的副本
  • 写：每次赋值都要写回 对象所在内存，不能只改寄存器，也不能把 中间几次写 合并成最后一次

这里举两个例子，下面汇编来自 gcc -O2，x86-64

连续两次写入 

void twiddle(int *p) {
    *p = 1;
    *p = 2;
}

void twiddle_v(volatile int *p) {
    *p = 1;
    *p = 2;
}

汇编如下：

twiddle:
    movl    $2, (%rcx)
    ret

twiddle_v:
    movl    $1, (%rcx)
    movl    $2, (%rcx)
    ret

普通指针下，编译器 认为中间写 1 没有可见副作用，直接只留下 *p = 2，volatile 之后，两次写都必须落到内存

循环里反复读 

void wait_flag(int *flag) {
    while (*flag == 0) {
    }
}

void wait_flag_v(volatile int *flag) {
    while (*flag == 0) {
    }
}

汇编如下：

wait_flag:
    movl    (%rcx), %eax
    testl   %eax, %eax
    je      .L6
    ret
.L6:
    jmp     .L6

wait_flag_v:
.L8:
    movl    (%rcx), %eax
    testl   %eax, %eax
    je      .L8
    ret

普通版本只读一次 *flag，若为 0 就进入死循环，之后再也不读内存，volatile 版本每次循环都重新 movl (%rcx), %eax

同一表达式里读两次 

int sum_twice(int *p) {
    return *p + *p;
}

int sum_twice_v(volatile int *p) {
    return *p + *p;
}

汇编如下：

sum_twice:
    movl    (%rcx), %eax
    addl    %eax, %eax
    ret

sum_twice_v:
    movl    (%rcx), %eax
    addl    (%rcx), %eax
    ret

普通版本读一次再加倍，volatile 版本对 *p 做两次内存读。若 p 指向的是会自己变化的 硬件寄存器，两次读本来就可以 不相等

应用场景

volatile 适合的，是 值会在 当前这段 C 代码的正常控制流 之外发生变化，或写出去必须立刻对 硬件可见 的情况：

  1. 内存映射 I/O（MMIO）

    外设寄存器 映射到某段地址，对这段地址的每一次读、写都可能有硬件副作用，不能被 编译器 合并 或 删掉

    #define REG_STATUS (*(volatile uint32_t *)0x40001000)

void wait_ready(void) {
    while ((REG_STATUS & 0x1u) == 0u) {
    }
}

  2. 信号处理函数里改、主流程里看的 标志

    标准做法是 volatile sig_atomic_t，信号 异步打断 执行流，没有 volatile 时，主循环可能把 标志 缓存在 寄存器 里，永远看不见 处理函数 里的 赋值

    volatile sig_atomic_t g_got_signal = 0;

void on_sigint(int signo) {
    (void)signo;
    g_got_signal = 1;
}

int main(void) {
    signal(SIGINT, on_sigint);
    while (!g_got_signal) {
        /* ... */
    }
    return 0;
}

  3. setjmp / longjmp 跨越的 局部变量

    longjmp 之后，若局部变量在 setjmp 之后被改过，又要在跳回后继续用，需要 volatile，否则优化后的值可能对不上

  4. 和 DMA、设备共享、会自己改的缓冲区指针

    例如 网卡写环式描述符，主机侧指针所指数值会在 CPU 不知情时变化，这类对象有时需要 volatile，或通过专门的访问接口保证 每次访存 都发生

不属于 volatile 该单独解决的问题：

  • 多线程共享数据 的 互斥、可见性、原子性 → 用 互斥锁、条件变量、atomic 等
  • 指望靠它当 便宜的原子变量 → 做不到，它不保证多字节读写的 原子性，也不插入 硬件内存屏障

为什么尽量不要使用 volatile

在 Linux 内核官方文档 中有这么一篇文章：

  • Why the “volatile” type class should not be used — The Linux Kernel documentation

它具体叙述了 为什么尽量不要使用 volatile

大概内容是：

  • 如果你要实现 并发同步，不要用 volatile 顶替 同步原语
  • spinlock、mutex、memory barrier 等本身就会 限制优化，并 保证 并发访问 的 规则
  • 在 已经 正确加锁 的 临界区 里再给共享数据加 volatile，只会让编译器在 明明独占 时也不能优化，带来无意义的 性能损失
  • 内核对 I/O 内存一般走 访问器函数，这些函数内部已经处理了 不能乱优化 的问题，业务代码通常不必自己声明 volatile

文档也承认 少数场景 仍会用到，例如 某些架构上的 I/O 访问器、带副作用的 asm volatile、历史遗留的 jiffies、以及设备会改写的一致内存里的 指针

这些和上面 应用场景 是同一类：异步变化 或 硬件可见，不是 普通 多线程共享变量

结语

volatile 做的是 抑制编译器对某个对象访存的优化，让每一次读、写都落到 对象本身

它解决的是 编译器以为值不会变 / 写可以合并 的问题，不是 多线程如何正确同步 的问题

不到对应场景，最好不要把一个变量声明为 volatile
